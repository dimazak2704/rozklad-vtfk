# Deployment — «Розклад ВТФК» on one VPS

The whole system runs on one Linux server behind Caddy, which gets Let's Encrypt certificates by
itself. You create the VM, point a domain at it, fill one env file and run one command:

```bash
infra/deploy/scripts/deploy.sh
```

The same command updates the server later. GitHub Actions can run it for you on every push to
`main` (section 13).

## 1. Layout

```
Internet ──► :80 / :443  Caddy (TLS, HTTP/2 + HTTP/3, security headers, compression)
              ├─ https://DOMAIN/            → web:80        nginx + Vite build, SPA fallback
              ├─ https://DOMAIN/api/*       → gateway:8080  → core, scheduler, importer, notification
              └─ https://DOMAIN/auth/*      → web:80 → auth:8085  sign-in page, OIDC, keys (/auth/internal/* → 404;
                                            nginx limits /auth/* to 5 requests a second per client address)
              (/api/internal/* and /api/import/ai/parse-absence → 404: service-to-service only)

Internal network only (no published ports): postgres, rabbitmq, redis, the services, auth's actuator.
```

Everything is on one origin, so the browser makes no cross-origin calls and one web image fits every
domain (the SPA signs in at `<its origin>/auth`).

| File | What it does |
|---|---|
| `infra/deploy/compose.prod.yml` | Overlay on `infra/docker-compose.yml`: Caddy, no published ports for anything else, `auth` in production mode, secrets from env, memory limits, log rotation, runtime hardening (no new privileges, no capabilities for the Java services, process limits, read-only Caddy and nginx, lower CPU weight for background work, at most one CPU for `auth`) |
| `infra/deploy/caddy/Caddyfile` | The site, TLS, routing of `/api` and `/auth`, the internal API of `auth` closed, forged forwarding headers removed |
| `infra/deploy/.env.example` → `infra/deploy/.env` | Every setting with comments. `.env` is gitignored |
| `infra/deploy/secrets/auth-signing-key.pem` | Token signing key of `auth` (RSA, created by `gen-secrets.sh`; gitignored) |
| `infra/deploy/postgres/20-prod-passwords.sh` | Replaces the dev passwords of `init.sql` on the first start, and every password again after a restore |
| `infra/deploy/rabbitmq/20-rozklad.conf` | The broker user gets no management tag |
| `infra/deploy/scripts/` | `deploy.sh`, `gen-secrets.sh`, `compose.sh`, `backup-db.sh`, `restore-db.sh`, `ci-entry.sh` (what the GitHub key may run) |
| `infra/deploy/.env.images` | Written by `deploy.sh`: which images run now (gitignored, do not edit) |
| `.github/workflows/ci.yml`, `deploy.yml` | CI and auto-deploy |

How this covers the coursework requirements (level A):

| Requirement | Here |
|---|---|
| Permanent public HTTPS link | `https://DOMAIN`, certificates renewed by Caddy, the VM is always on (no cold starts) |
| Client, server and database deployed separately | Separate containers: nginx with the SPA, Spring services behind the gateway, the sign-in service, PostgreSQL |
| Secrets only in environment variables | `infra/deploy/.env` (gitignored), generated by `gen-secrets.sh`; the repo has only `.env.example` |
| CORS for the deployed client | Gateway `CORS_ALLOWED_ORIGINS` = `https://DOMAIN`; the SPA, the API and the sign-in share that origin |
| SPA routing on the static server | nginx `try_files … /index.html` |
| Test credentials | The first admin and the demo teachers from `.env` (section 9) |
| Auto-deploy from `main` with GitHub Actions | `.github/workflows/deploy.yml` |

## 2. Create the server

Recommended: 4 vCPU, 8+ GB RAM, 40+ GB disk, Ubuntu 24.04, x86_64 or ARM64; for the defense take
8 GB or the Oracle A1 VM below. The memory limits of the containers add up to about 6 GB (they are
caps, not reservations). 2 vCPU / 4 GB with 2 GB of swap is best effort and has not been measured:
on such a server let GitHub Actions build the images (section 13) instead of building on the VPS,
and watch `docker stats --no-stream` while the solver runs.

**Oracle Cloud Always Free (recommended, 4 OCPU / 24 GB ARM64, free).**

1. Sign up at cloud.oracle.com. A card is checked but Always Free resources are not charged. The
   **home region cannot be changed later** and the free A1 capacity exists only there: pick one close
   to Ukraine (Frankfurt, Amsterdam, Stockholm…).
2. Compute → Instances → Create instance.
   - Image: Canonical Ubuntu 24.04. Shape: Ampere → `VM.Standard.A1.Flex`, 4 OCPU, 24 GB.
   - Networking: create a VCN with a public subnet, "Assign a public IPv4 address".
   - SSH keys: upload your public key (`~/.ssh/id_ed25519.pub`) or download the generated one.
   - Boot volume: 100 GB is plenty (200 GB of block storage are free in total).
3. "Out of capacity" is common for A1: try another availability domain, try again later, or take
   2 OCPU / 12 GB for now.
4. To keep the address when the VM is recreated, make the public IP **reserved** (Networking → IP
   management → Reserved public IPs, then attach it on the instance's VNIC).
5. Oracle may reclaim Always Free VMs that stay idle for 7 days (CPU, network and, for A1, memory
   under 20 %). Upgrading the account to Pay As You Go keeps the free resources free and stops that.

Log in: `ssh ubuntu@<public-ip>`.

**Other options.** Azure for Students ($100 credit, no card): a `B2s` / `B2als v2` VM with 4 GB and
Ubuntu 24.04 lasts a few months on the credit (a 4 GB size is best effort, see above; `B2ms` has
8 GB). Any other VPS works the same way; the user name may be `root` or `azureuser` instead of
`ubuntu`.

## 3. Open ports 80 and 443, prepare the OS

Ports 80 and 443 must be open in **two places**: the cloud firewall and the OS firewall. Port 80 is
needed for the Let's Encrypt challenge and the redirect to HTTPS. UDP 443 (HTTP/3) is optional.

Cloud firewall:
- Oracle: Networking → Virtual cloud networks → your VCN → Security Lists → Default Security List →
  Add Ingress Rules: source `0.0.0.0/0`, TCP, destination port `80`; the same for `443`
  (optionally UDP `443`).
- Azure: VM → Networking → Add inbound port rule: 80 and 443 (TCP).

OS firewall. Oracle's Ubuntu images ship iptables rules that reject everything except SSH. Open the
ports **before installing Docker**, so the saved rules do not contain Docker's own chains:

```bash
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p udp --dport 443 -j ACCEPT
sudo netfilter-persistent save
sudo iptables -L INPUT -n --line-numbers   # the three ACCEPT lines must be above the REJECT line
```

On images with ufw instead (Azure, most VPS): `sudo ufw allow OpenSSH && sudo ufw allow 80,443/tcp &&
sudo ufw allow 443/udp && sudo ufw enable`. Docker publishes ports with its own iptables rules that
bypass ufw; that is one more reason why only Caddy publishes ports here.

Docker Engine with the Compose plugin (the official script works on x86_64 and ARM64):

```bash
curl -fsSL https://get.docker.com -o get-docker.sh && sudo sh get-docker.sh
sudo usermod -aG docker "$USER"     # log out and back in for this to apply
docker compose version              # needs 2.24.4 or newer
```

On a 4 GB server add 2 GB of swap (the builds need it):

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Optional: `sudo timedatectl set-timezone Europe/Kyiv` (cron times of the backup).

**Harden the server** before the first deploy. The site is public, and the `docker` group of your
user is root-equivalent, so the SSH login is the key to everything.

SSH with keys only and no root login (most cloud images already do this; the file makes it explicit).
Keep the current session open and check that a second `ssh` login works before you close it:

```bash
sudo tee /etc/ssh/sshd_config.d/90-rozklad.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
sudo sshd -t && sudo systemctl reload ssh
```

Limit password guessing on port 22: with ufw use `sudo ufw limit OpenSSH` instead of `allow`; on
Oracle's iptables images `sudo apt-get install -y fail2ban` (its `sshd` jail is on by default). If your
own IP is stable, allow port 22 only from it in the cloud firewall. Do not add other users to the
`docker` group.

Security updates, Docker Engine included: `get.docker.com` installs Docker from Docker's own apt
repository, which `unattended-upgrades` skips by default, so container-escape fixes in `containerd` and
`runc` would never arrive by themselves:

```bash
sudo apt-get install -y unattended-upgrades
sudo tee /etc/apt/apt.conf.d/52unattended-rozklad >/dev/null <<'EOF'
Unattended-Upgrade::Origins-Pattern { "origin=Docker"; };
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "04:30";
EOF
sudo unattended-upgrade --dry-run --debug 2>&1 | grep -i 'origin=Docker'   # Docker's packages are allowed now
```

An update of Docker Engine restarts the daemon and with it the containers (they come back by
themselves, `restart: unless-stopped`), and a kernel update reboots the server at 04:30: a minute of
downtime at night.

## 4. Domain names

One host name points to the server: `DOMAIN`.

| Option | DOMAIN | DNS work |
|---|---|---|
| sslip.io (free, nothing to register) | `203-0-113-10.sslip.io` for IP 203.0.113.10 | none |
| DuckDNS (free) | `rozklad-vtfk.duckdns.org` | create the name at duckdns.org with the server IP |
| GitHub Student Developer Pack | a free domain for a year from a partner registrar (see education.github.com/pack for the current offer) | an A record |
| Own domain | `rozklad.example.org` | an A record `rozklad` → server IP (no AAAA, see below) |

Create an **A record only, no AAAA (IPv6) record**. Caddy publishes its ports on IPv4 only
(`compose.prod.yml`): the compose network has no IPv6, so Docker would pass every IPv6 visitor to Caddy
under one internal address, and they would all share one bucket of the per-IP rate limit and one
sign-in throttle. Turning IPv6 on needs `enable_ipv6` with its own subnet on the compose network and a
check with `curl -6` that the gateway and `auth` logs show the real addresses.

Do not put a CDN or proxy such as Cloudflare (orange cloud) in front without changing the Caddyfile:
Caddy would see only the CDN's addresses, and every visitor would share their buckets. If you need one,
in the Caddyfile's global options set `servers { trusted_proxies static <the CDN's published ranges>
client_ip_headers CF-Connecting-IP }` and add `header_up X-Forwarded-For {client_ip}` to every
`reverse_proxy`, so the gateway and `auth` get exactly one address that Caddy has checked. Simply
trusting the CDN is not enough: the gateway reads the leftmost `X-Forwarded-For` value, which the
client controls. "DNS only" (grey cloud) needs no change.

Check before deploying: `getent hosts rozklad.example.org` on the server (or `nslookup` on Windows).
sslip.io depends on the IP never changing (reserve it) and on a public DNS service; Let's Encrypt raised
its limits for sslip.io/nip.io, and if a certificate is still refused, `<ip>.nip.io` or a DuckDNS name
works the same way. Google sign-in on the server needs a redirect URI on this host
(`docs/GOOGLE_SIGNIN.md`); whether Google accepts sslip.io names has not been checked.

## 5. Get the code and configure

```bash
git clone https://github.com/<user>/<repo>.git ~/rozklad
cd ~/rozklad
infra/deploy/scripts/gen-secrets.sh     # creates infra/deploy/.env, fills every "change-me", makes the signing key
nano infra/deploy/.env
```

A private repository needs a read-only deploy key on the server: `ssh-keygen -t ed25519 -f
~/.ssh/rozklad_deploy -N ''`, add `~/.ssh/rozklad_deploy.pub` in GitHub → repository → Settings →
Deploy keys, then clone with `GIT_SSH_COMMAND='ssh -i ~/.ssh/rozklad_deploy' git clone
git@github.com:<user>/<repo>.git ~/rozklad` and run `git config core.sshCommand 'ssh -i
~/.ssh/rozklad_deploy'` inside the clone.

Set by hand in `infra/deploy/.env`:

| Key | Value |
|---|---|
| `DOMAIN` | host name only, e.g. `rozklad.example.org` or `203-0-113-10.sslip.io` |
| `ACME_EMAIL` | your real e-mail (Let's Encrypt refuses example.com) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_CHAT_ID`, `TELEGRAM_BOT_USERNAME` | from @BotFather / your chat (section 10) |
| `ANTHROPIC_API_KEY` | from console.anthropic.com; empty disables AI import |
| `AUTH_GOOGLE_*` | optional: Google sign-in (`docs/GOOGLE_SIGNIN.md`); empty = password sign-in only |
| memory block at the end | uncomment it on Oracle A1 (24 GB); keep the defaults on 4–8 GB |

Everything else has a working default or was generated. The secrets never leave this file: compose
passes each service only what it needs. Keep a copy of `.env` in a password manager — backups depend
on these values. The signing key (`infra/deploy/secrets/`, directory 700, file 644 so that the container
user of `auth` can read the bind-mounted file) needs no backup: a lost key is replaced (section 11).

Create the backup directory once: `sudo install -d -m 700 -o "$USER" /var/backups/rozklad`.

## 6. First start

```bash
infra/deploy/scripts/deploy.sh
```

What it does:

1. `git pull --ff-only` and continues with the scripts it just pulled (`--no-pull` skips this).
2. Preflight: Docker and Compose versions, no `change-me` left, sane `DOMAIN`/`ACME_EMAIL`, the
   signing key exists, the compose configuration renders, warnings about RAM without swap and while
   `AUTH_BOOTSTRAP_ADMIN_PASSWORD` is still set (empty it after your first sign-in).
3. Builds the jars with Maven in a `maven:3.9.11-eclipse-temurin-25` container (no JDK on the host,
   dependencies cached in `~/.m2`), then the images `localhost/rozklad/<service>:prod` for this CPU
   (`compose build --pull`). With GitHub-built images it pulls them instead (section 13). Either way
   it records the images in `infra/deploy/.env.images`, so `compose.sh` and `restore-db.sh` keep
   using exactly those.
4. `compose up -d --wait`: PostgreSQL creates the databases (dev `init.sql`, then the production
   passwords); `auth` registers the clients with the secrets of `.env`, creates the first admin and the
   demo teachers (section 9) and becomes ready once an admin can sign in; the services start; Caddy
   requests the certificate.
5. `caddy reload` (a changed Caddyfile takes effect).
6. Smoke checks through Caddy (SPA, API, per-client rate limit with forged `Forwarded` headers, the
   issuer `https://DOMAIN/auth`, the sign-in redirect on this origin, `/auth/internal` and
   `/api/internal` closed, certificate) and a summary.
   In pull mode it then removes the images of older deploys, keeping the current and the previous
   one.

The first run downloads a lot (Maven dependencies, LibreOffice packages for the notification image, npm
packages) and takes roughly 15–30 minutes. Later runs take a few minutes. If a step fails, the script stops with the command to look at; it is
safe to run again.

## 7. Check that it works

```bash
D=rozklad.example.org    # your DOMAIN
curl -sI https://$D/ | grep -iE '^(HTTP|strict-transport|content-security-policy)'
curl -s https://$D/auth/.well-known/openid-configuration | grep -o '"issuer":"[^"]*"'
curl -s -o /dev/null -w '%{http_code}\n' https://$D/auth/internal/accounts  # 404: internal API closed
curl -si https://$D/api/public/does-not-exist | grep -iE '^(HTTP|x-request-id)'   # the gateway answered
curl -sI http://$D/ | grep -i '^location'                                    # redirect to https
```

Expected: `HTTP/2 200` with HSTS and a CSP with `connect-src 'self'`; issuer `https://DOMAIN/auth`;
`404`; a 404 with an `X-Request-Id` header; `location:
https://…`.

In the browser: open `https://DOMAIN`, sign in as the first admin (section 9), open the admin pages;
in a private window sign in as `krentsin`. Live updates (SSE) can be checked with a token copied from the browser
(DevTools → Network → any `/api` request → `Authorization` header):

```bash
curl -N -H "Authorization: Bearer <token>" https://$D/api/events/stream    # "event: ping" every ~25 s
```

For the explanatory note, run Lighthouse (mobile) against `https://DOMAIN` here.

## 9. Accounts for the examiner

**The first admin.** On the first start `auth` creates the account `AUTH_BOOTSTRAP_ADMIN_USERNAME`
(default `admin`) with `AUTH_BOOTSTRAP_ADMIN_PASSWORD` (`gen-secrets.sh` generated it; read it in
`.env`). It does this only while no admin can sign in, and `auth` does not become ready before that.
After your first sign-in, empty the value (`AUTH_BOOTSTRAP_ADMIN_PASSWORD=`) and run `deploy.sh`.
Forgotten admin password (break-glass): put a new password into `AUTH_BOOTSTRAP_ADMIN_PASSWORD`, set
`AUTH_BOOTSTRAP_FORCE=true`, run `infra/deploy/scripts/compose.sh up -d auth`, sign in, then set
`AUTH_BOOTSTRAP_FORCE=false`, empty the password and run the same command again.

**Demo teachers.** Every start of `auth` brings these accounts in line with `.env`:

| Login | Role | Password |
|---|---|---|
| `krentsin` | TEACHER | `DEMO_TEACHER_PASSWORD` |
| `nepyivoda` | TEACHER | `DEMO_TEACHER_PASSWORD` |

Give the logins in the explanatory note or on paper, never in the repository. They keep the ids of the
development accounts, so demo data that links the teachers «Кренцін» and «Непийвода» to those ids works
on the server too. To change the password, edit `.env` and run `infra/deploy/scripts/compose.sh up -d auth`.
After the defense empty `DEMO_TEACHER_PASSWORD` and run the same command: both accounts are disabled and
signed out, and every later start (also the GitHub deploy and `restore-db.sh`) keeps them off. A demo
account revoked on «Доступи» stays revoked. For an examiner who needs the admin pages, sign in as the
admin and grant access on «Доступи» (`/admin/access`): an e-mail, the role ADMIN, and a password link
from the row menu.

Real teachers join through invites (`/invite/{token}`) or get access by e-mail on «Доступи» (Google or a
password link); self-registration is off. Passwords need 12 to 64 characters, must differ from the login
and the e-mail and must not be a common password; five wrong passwords in a row lock the login for a while.

## 10. Telegram bot

Long polling (the default `TELEGRAM_MODE=POLLING`) needs no inbound connection, but **one bot token
can be polled by one process only**. A second poller makes Telegram answer `409 Conflict: terminated
by other getUpdates request` and the two instances steal updates from each other. Before starting
the server, stop the notification service on your PC (or the local `--profile app` stack), or better:
create a second bot in @BotFather for development and keep its token in your local `.env`.

`TELEGRAM_OWNER_CHAT_ID` is your chat id (write to the bot, then read `chat.id` from
`https://api.telegram.org/bot<token>/getUpdates` while no instance is polling). Webhook mode
(`TELEGRAM_MODE=WEBHOOK`) registers `https://DOMAIN/api/notify/telegram/webhook` (`compose.prod.yml` derives
`TELEGRAM_WEBHOOK_URL` from `DOMAIN`; set it in `.env` only to override) and checks the
`TELEGRAM_WEBHOOK_SECRET` header; Caddy already provides the HTTPS endpoint. Without a URL the bot only sends,
and `GET /api/notify/bot` reports it in `problem`.

## 11. Day-to-day operations

`infra/deploy/scripts/compose.sh` is `docker compose` with the production files; use it for
everything:

```bash
cd ~/rozklad
infra/deploy/scripts/deploy.sh                               # update to the latest main (see below)
infra/deploy/scripts/compose.sh ps                           # status and health
infra/deploy/scripts/compose.sh logs -f --tail=100 core      # follow one service
infra/deploy/scripts/compose.sh logs --since=1h notification | grep -i error
infra/deploy/scripts/compose.sh restart notification         # same container, same environment
infra/deploy/scripts/compose.sh up -d                        # apply .env changes (recreates what changed)
infra/deploy/scripts/compose.sh exec postgres psql -U postgres -d core
infra/deploy/scripts/compose.sh exec rabbitmq rabbitmqctl list_queues name messages consumers
docker stats --no-stream                                     # memory per container
```

The broker user `RABBIT_USER` has no management tag (`infra/deploy/rabbitmq/20-rozklad.conf`): the
services need AMQP only, and a leaked password must not open the management API. Use `rabbitmqctl` in
the container as above. Only `core`, `scheduler` and `notification` get the broker password; `importer`
has no AMQP client and `scheduler` no Redis client, so they do not get those passwords.

The Java services log JSON (ECS). Readable view: `sudo apt-get install -y jq`, then
`infra/deploy/scripts/compose.sh logs --no-log-prefix core | jq -r '"\(.["@timestamp"]) \(.["log.level"]) \(.message)"'`.
Docker rotates the logs: 5 files × 10 MB per container.

`compose.sh` always uses the images recorded in `infra/deploy/.env.images` by the last `deploy.sh`
(also the one GitHub ran), so `compose.sh up -d` never switches images behind your back. `restart`
keeps a container's old environment: after changing `.env` use `up -d`.

Which images `deploy.sh` rolls out: `IMAGE_PREFIX`/`IMAGE_TAG` from the environment, else from `.env`,
else the recorded ones, else `localhost/rozklad/<service>:prod` built on the server. So on a server fed
by GitHub Actions a manual `deploy.sh` pulls the scripts and compose files of `main` and starts the
same images again; new images come only from the Deploy workflow. `deploy.sh --build` builds on the
server instead.

`TELEGRAM_BOT_USERNAME` is baked into the SPA (the bot link) when the web image is built: with images
built on the server change `.env` and run `deploy.sh`; with images from GitHub Actions change the
repository variable too and run the Deploy workflow (Actions → Deploy → Run workflow on `main`).

`DOMAIN` is not baked into any image. A new `DOMAIN`: change `.env` on the server and the repository
variable `DOMAIN` (`ci-entry.sh` refuses to deploy while they differ), then run `deploy.sh`. Caddy gets
the new certificate, `auth` registers the new redirect URIs and issuer, and everybody signs in again.

Rollback to an earlier commit:

```bash
git log --oneline -10
git checkout <good-commit> && infra/deploy/scripts/deploy.sh --no-pull
git checkout main                              # later, to follow main again
```

With images from GitHub Actions: `IMAGE_TAG=<good-commit-sha> infra/deploy/scripts/deploy.sh --no-pull
--pull-images` (the prefix comes from the record). The previous deploy's images stay on the server;
older ones are pulled again, which needs `docker login ghcr.io` for private packages (section 13).
Database migrations only go forward (Flyway), so roll back only to a commit with the same schema, or
restore a backup.

Accounts are managed in the SPA: «Доступи» (`/admin/access`) for roles, revoke and restore, password
links and Google bindings; the teacher pages for invites and account links. For a quick look at the
database: `infra/deploy/scripts/compose.sh exec postgres psql -U postgres -d auth -c 'SELECT username,
email, enabled, disabled_reason FROM account'`.

**Signing key.** Rotation: `mv infra/deploy/secrets/auth-signing-key.pem{,.old}`, run
`infra/deploy/scripts/gen-secrets.sh` (a new key and a new `AUTH_SIGNING_KEY_ID`), then
`infra/deploy/scripts/compose.sh up -d auth` and delete the `.old` file. Access tokens of the old key
stop working (they live 5 minutes); the SPA renews them through the sign-in session, so nobody has to
sign in again, and the services fetch the new key by its new `kid`. If the key may have leaked, do the
same, then end every sign-in and drop the cached keys:

```bash
infra/deploy/scripts/compose.sh exec postgres psql -U postgres -d auth \
  -c 'DELETE FROM oauth2_authorization' -c 'DELETE FROM spring_session'
infra/deploy/scripts/compose.sh restart core scheduler importer notification
```

## 12. Backups and restore

```bash
infra/deploy/scripts/backup-db.sh        # all databases incl. auth → /var/backups/rozklad/rozklad-<date>.sql.gz[.age]
crontab -e                               # daily at 03:15, keeps BACKUP_KEEP_DAYS (14) days:
15 3 * * * $HOME/rozklad/infra/deploy/scripts/backup-db.sh >>$HOME/rozklad-backup.log 2>&1
```

A dump is the whole cluster: every account with its password hash, the sign-in sessions and the
Telegram chat bindings. On the server the files are readable by your user only. Dumps that stay on the
VM are lost with it (a deleted or reclaimed Always Free VM, a failed disk), so set up the encrypted
off-site copy below before real data goes in, and never keep the dumps next to `.env` (that file
belongs in a password manager, section 5).

**1. Encrypt on the server.** With [age](https://age-encryption.org) the server gets only the public
key; the private key stays on your PC and in the password manager, so even a stolen server cannot read
its own backups. On your PC (Windows: `winget install FiloSottile.age`), outside the repository:

```bash
mkdir -p ~/rozklad-backups && cd ~/rozklad-backups
age-keygen -o rozklad-backup.key        # once; keep it in the password manager, never on the server
# the public key is the "public key: age1..." line it printed
```

On the server: `sudo apt-get install -y age`, then in `infra/deploy/.env`:
`BACKUP_AGE_RECIPIENT=age1...` (the public key). From now on every dump is
`rozklad-<date>.sql.gz.age`; the plain dump exists only in the pipe.

**2. Copy off-site on every run.** Install [rclone](https://rclone.org/install/) on the server
(`sudo apt-get install -y rclone`, or the official script for a current version), run `rclone config`
and create a remote for any storage you have: Oracle Object Storage (S3-compatible, free tier),
Backblaze B2, Google Drive of the college account. Then in `.env`:
`BACKUP_RCLONE_REMOTE=<remote>:<bucket or folder>`. The script refuses an off-site copy without
`BACKUP_AGE_RECIPIENT`. It only copies; let the storage delete old copies with a lifecycle rule (for
example after 60 days) and, where the storage allows it, give the server a key that can write but not
delete: then even an attacker on the server cannot wipe the off-site copies. A failed copy makes the
run fail, and the local dump stays.

**3. Notice when it stops.** `BACKUP_PING_URL=https://hc-ping.com/<uuid>` (a free healthchecks.io
check with a period of 1 day): the script fetches it only after a fully successful run, so a broken
cron, a full disk or a failed copy turns into an e-mail. Also turn on the provider's volume backups
if they are free (Oracle: boot volume backup policy).

**4. Try a restore once per term** on a copy, not on production: on your PC
`age -d -i rozklad-backup.key -o test.sql.gz rozklad-<date>.sql.gz.age`, then load it into a
throwaway PostgreSQL (`docker run --rm -d --name pg-restore-test -e POSTGRES_PASSWORD=x postgres:18-alpine`,
`gunzip -c test.sql.gz | docker exec -i pg-restore-test psql -q -U postgres`), look at a few rows,
remove the container and the plain file, and note the date in section 16.

Restore (destructive: every database is replaced):

```bash
infra/deploy/scripts/restore-db.sh /var/backups/rozklad/rozklad-20261107-031500.sql.gz --yes
```

An encrypted dump is decrypted on your PC (the private key never goes to the server) and the plain
dump is streamed to the server: `age -d -i rozklad-backup.key rozklad-20261107-031500.sql.gz.age |
ssh ubuntu@<ip> 'umask 077; cat >/tmp/restore.sql.gz'`, then `restore-db.sh /tmp/restore.sql.gz
--yes` and `rm /tmp/restore.sql.gz`. `restore-db.sh` refuses an `.age` file with this hint.

It first checks that the recorded images are on the server (otherwise it stops before touching
anything), then stops everything except PostgreSQL, loads the dump (two errors about the role
`postgres` are expected), sets every database password from the current `.env` again (the dump carries
the old cluster's, the superuser's included), starts the same images; `auth` applies the client secrets and demo teachers of `.env` when it starts. On a new
server: deploy first, then restore.

Volumes: `pgdata` holds all data. `rabbitdata` (queued messages), `redisdata` (caches, bot dialogs)
and `caddy_data` (certificates, re-issued automatically) can be lost without harm.
`infra/deploy/scripts/compose.sh down -v` deletes all of them.

## 13. GitHub Actions

- **CI** (`.github/workflows/ci.yml`) runs on pull requests and on pushes to other branches: Maven
  `verify` on JDK 25 (unit tests and Testcontainers integration tests with the runner's Docker),
  web `npm ci`, lint, tests, build, and checks of this deployment setup (compose overlay, Caddyfile,
  shell scripts, and `infra/deploy/tests/run.sh`: the deploy-key checks of `ci-entry.sh`, the
  backups, Caddy routing and the broker and database users in throwaway containers, and the
  rendered compose files: ports, credentials per service, container hardening, pinned actions).
- **Deploy** (`.github/workflows/deploy.yml`) runs on every push to `main` and by hand: it calls CI,
  and only if CI passes builds the images for `linux/amd64` and `linux/arm64`, pushes them to
  `ghcr.io/<owner>/rozklad/<service>:<commit-sha>` and `:latest`, then connects to the server over
  SSH and runs `infra/deploy/scripts/ci-entry.sh`, which runs `deploy.sh --pull-images --fresh` with
  that tag. A manual run on any branch other than `main` runs CI only.
- **Weekly rebuild.** Every Monday at 02:23 UTC Deploy runs for the current `main` without a push:
  the images are built again on the current base images (JRE, nginx, Alpine and Ubuntu packages) and
  rolled out, so their security fixes reach the server; `--fresh` makes the server pull them although
  the commit tag is the same. The services restart once (a minute or two at night). GitHub pauses
  scheduled runs after 60 days without commits; Actions → Deploy shows it.
- **Dependabot** (`.github/dependabot.yml`) opens weekly pull requests for Maven, npm, the base images
  of the Dockerfiles, the images of the compose files and the actions. Third-party actions are pinned
  to a commit SHA (Dependabot updates the SHA), because the image job can push packages. PostgreSQL
  majors are ignored (a new major cannot read the data volume).

Deploy does nothing but CI until the variable `DOMAIN` is set. Create the environment `production`
first (step 1 of "Repository settings" below) and put the secrets there (Settings → Environments →
`production` → Environment secrets); the variables go to Settings → Secrets and variables → Actions →
Variables. Only the deploy job, which names `production`, reads the secrets; repository secrets
still work but any workflow on any branch could read those.

| Kind | Name | Value |
|---|---|---|
| environment secret | `VPS_HOST` | server IP or DOMAIN |
| environment secret | `VPS_USER` | `ubuntu` (the user that owns `~/rozklad` and is in the `docker` group) |
| environment secret | `VPS_SSH_KEY` | private key of a key pair made for GitHub (below) |
| environment secret | `VPS_KNOWN_HOSTS` | the server's host key (below); the deploy job fails without it |
| environment secret, optional | `VPS_PORT` | SSH port if not 22 |
| variable | `DOMAIN` | switches deployment on; the same value as in `.env` (the deployment URL; `ci-entry.sh` compares them) |
| variable, optional | `IMAGE_PLATFORMS` | `linux/arm64` for Oracle A1 only: about half the build time |
| variable, optional | `VPS_APP_DIR` | clone directory on the server, default `rozklad` (= `~/rozklad`) |
| variable, optional | `TELEGRAM_BOT_USERNAME` | bot link on the About page |

Deploy key for GitHub. The `docker` group is root-equivalent, so the key must not open a shell: it
gets a forced command and may run `ci-entry.sh` only. On your PC:

```bash
ssh-keygen -t ed25519 -C github-deploy -f ~/.ssh/rozklad_github -N ''   # outside the repository
cat ~/.ssh/rozklad_github.pub                  # one line: ssh-ed25519 AAAA... github-deploy
```

On the server, append that line to `~/.ssh/authorized_keys` **with this prefix** (adjust the path if
the clone is not `~/rozklad` of the user `ubuntu`):

```
restrict,command="bash /home/ubuntu/rozklad/infra/deploy/scripts/ci-entry.sh" ssh-ed25519 AAAA... github-deploy
```

`restrict` turns off port forwarding, agent forwarding and the terminal; `command` makes sshd run
`ci-entry.sh` whatever the client asks. The script reads the commit sha, image prefix, user name,
token and `DOMAIN` from stdin, and the server decides what it accepts, because whoever holds the key
chooses those lines:

- the image prefix must be this server's own: `DEPLOY_IMAGE_PREFIX` in `.env` if set, otherwise
  `ghcr.io/<GitHub owner of the clone's origin, lower-case>/rozklad`. Images of another GHCR owner are
  refused before the server logs in anywhere. A clone whose origin is not on GitHub needs
  `DEPLOY_IMAGE_PREFIX`;
- the commit must be the tip of `main` on origin right now (`git fetch` on the server). An older
  commit is refused, so the key cannot roll production back. If two pushes come quickly, the run of
  the older one stops at this check and the run of the newer one deploys;
- `DOMAIN` must equal the server's.

Then it runs `deploy.sh --pull-images`. A leaked key can therefore only redeploy the current `main`;
still treat it like a password. Paste the private key into the `VPS_SSH_KEY` secret, then delete both
files.

Host key: on the server run `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`; on your PC run
`ssh-keyscan -t ed25519 <VPS_HOST>` (the same name or IP as the secret; `-p <port>` if not 22), check with `ssh-keygen -lf -` on that
output that the fingerprint is the same, and paste the `ssh-keyscan` line into `VPS_KNOWN_HOSTS`. The
runner never trusts a key it has not been given.

**Repository settings, before the secrets go in** (the repository is public, and a push to `main`
deploys):

1. Settings → Environments → New environment `production` → Deployment branches and tags: "Selected
   branches and tags", add `main`. Put `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS` (and
   `VPS_PORT`) here as **environment secrets**, not repository secrets: then only a job of `main` that
   names this environment can read them, not a workflow pushed to some other branch. Optionally add
   yourself as a required reviewer, so every deploy waits for your click (the weekly rebuild too).
2. Settings → Rules → Rulesets → New branch ruleset for `main`: block force pushes and deletion,
   require a pull request (you can allow yourself to bypass it) and the status checks of CI
   (Backend, Web, Deployment config).
3. Settings → Code security: Dependabot alerts and Dependabot security updates on; secret scanning
   and push protection stay on.
4. Settings → Actions → General: allow GitHub's actions and actions of verified creators only (the
   workflows use `actions/*` and `docker/*`), and keep the default `GITHUB_TOKEN` permission
   read-only.

Leave `IMAGE_PREFIX`/`IMAGE_TAG` unset in the server's `.env`. `deploy.sh` records what the workflow
deployed in `infra/deploy/.env.images`, and manual runs start those images again. The workflow logs
the server in to GHCR with the job's own token for the duration of the job, so the packages may stay
private; pulling other tags by hand needs `docker login ghcr.io` with a token that has
`read:packages`, or public packages. The server still runs `git pull` for the compose files and
scripts (deploy key for a private repo, section 5).

The first image build takes long (ARM64 is emulated with QEMU, the LibreOffice packages of notification and npm run inside it);
later builds reuse the GitHub Actions cache.

## 14. Troubleshooting

**`exec format error`, a container restarts at once.** The image was built for another CPU. Build on
the server (`deploy.sh --build`) or include its platform in `IMAGE_PLATFORMS`. Check with
`docker image inspect localhost/rozklad/core:prod --format '{{.Architecture}}'` (or the ghcr.io name) and `uname -m`
(`aarch64` = `arm64`).

**No certificate / the browser warns.** DNS of `DOMAIN` must point to the server,
TCP 80 and 443 must be open in both firewalls. `infra/deploy/scripts/compose.sh logs caddy | grep -iE
'error|challenge'`. After too many failures Let's Encrypt pauses for an hour: switch `ACME_CA` to the
staging URL while experimenting, then back, and run `compose.sh up -d caddy` each time (`restart`
keeps the old environment, so Caddy would stay on the old CA). With `ACME_CA` on staging browsers
always warn.

**Ports are open in the cloud but connections time out (Oracle).** `sudo iptables -L INPUT -n
--line-numbers` (section 3); `sudo iptables -L FORWARD -n | head`: Docker's chains must come before
`REJECT` — `sudo systemctl restart docker` puts them back on top.

**`auth` stays unhealthy, `deploy.sh` waits.** `compose.sh logs auth`. «auth refuses to start with an
https issuer» lists what is wrong (no signing key, a development secret, http origins, the Google mock).
A started service that never becomes ready has no admin who can sign in: set
`AUTH_BOOTSTRAP_ADMIN_PASSWORD` (12 characters at least; the log names a rejected one) and run
`compose.sh up -d auth`.

**The sign-in page answers 400 «invalid_request» / redirect_uri.** The site was opened on another
address than `https://DOMAIN` (the IP, `www.`): `auth` knows only the redirect URIs of `DOMAIN`.

**After sign-in the browser lands on `http://…` or on a port.** `auth` builds its redirects from Caddy's
`X-Forwarded-Proto` and `Host`; it trusts them only from the containers of the compose network
(`AUTH_TRUSTED_PROXIES` = its `ip_range` 172.29.1.0/24; the network gateway is outside it). The
smoke check «an authorize request without a session goes to https://DOMAIN/auth/login» covers it.

**Every API call returns 401 after a successful login (issuer mismatch).** Services accept only tokens
whose `iss` equals `AUTH_ISSUER` = `https://DOMAIN/auth` and whose `aud` contains `rozklad-api`.
Compare with the discovery document (section 7) and with the token (decode the middle part). Tokens
issued before `DOMAIN` changed are rejected: sign in again. `compose.sh exec core printenv AUTH_ISSUER`
shows what the service expects.

**Live updates (SSE) arrive late, in bursts, or stop.** The Caddyfile flushes `/api/events/stream`
immediately and does not compress it; the gateway route has no response timeout; core sends `ping`
every 25 s, so idle proxies do not cut the stream, and the SPA reconnects. Test with `curl -N`
(section 7). An extra proxy in front (Cloudflare and the like) has to be configured not to buffer.

**429 Too Many Requests on public pages.** The gateway limits `/api/public/**` per client IP
(`PUBLIC_RATE_LIMIT_PER_SECOND`, `PUBLIC_RATE_LIMIT_BURST`). Behind Caddy the gateway reads the real
client IP from `X-Forwarded-For` (`SERVER_FORWARD_HEADERS_STRATEGY=native`), so one user cannot
exhaust the limit of everyone. Other routes have their own per-IP buckets with gateway defaults: order
documents `DOCUMENTS_RATE_LIMIT_PER_SECOND=10` / `DOCUMENTS_RATE_LIMIT_BURST=30`, the rest of the API
`API_RATE_LIMIT_PER_SECOND=50` / `API_RATE_LIMIT_BURST=150` (to change them, pass these variables to
the gateway in `compose.prod.yml`). Caddy writes that header itself and removes the client's `Forwarded`,
`X-Forwarded-Port` and `X-Forwarded-Prefix` (snippet `strip_client_forwarding`); otherwise a forged
`Forwarded: for=...` would give every request a fresh bucket. Raise the values in `.env` if needed
and run `compose.sh up -d`.

**429 «Забагато запитів до входу» at sign-in.** Caddy sends `/auth/*` through the web nginx, which
allows 5 requests a second per client address, 20 more at once and 20 more after a short delay
(`limit_req` in `web/nginx.conf`): every anonymous visit of the sign-in page creates a session row in
auth's database, so one client must not be able to fill it. A sign-in takes about ten requests. Staff
behind the college's one public address share the limit; if they hit it at the start of the day, raise
`rate` in `limit_req_zone` and `burst` in `location /auth/` of `web/nginx.conf` and deploy the web image.
nginx trusts `X-Forwarded-For` only from the containers of the compose network (`set_real_ip_from`, the
`ip_range` of `infra/docker-compose.yml`): keep the two equal. `auth` itself may use at most one CPU
(`AUTH_CPUS`).

**PostgreSQL: "password authentication failed for user core".** The init scripts run only when the
volume is created. If the first start failed half-way, on a fresh server remove the volumes and start
again: `infra/deploy/scripts/compose.sh down -v && infra/deploy/scripts/deploy.sh` (**deletes all
data**). On a server with data, set the passwords from `.env` instead:
`infra/deploy/scripts/compose.sh exec postgres bash /docker-entrypoint-initdb.d/20-prod-passwords.sh`.

**Containers restart, `docker stats` shows them at the limit, `dmesg | grep -i oom` has entries.**
Add swap or raise the limits (memory block in `.env`); the JVMs exit on `OutOfMemoryError` and Docker
restarts them.

**Telegram: `409 Conflict`.** Another instance polls the same token (section 10).

**Disk full.** `docker system df`; `docker builder prune -f` and `docker image prune -f` free most of
it. `deploy.sh` prunes dangling images itself and, with GitHub-built images, removes the commit tags
of older deploys (it keeps the current and the previous one). Pulled tags of another prefix are not
touched: `docker image ls` and `docker image rm` them by hand.

## 15. For the explanatory note (section 4.7.9)

- Platform: one VPS (Oracle Cloud Always Free, Ampere A1, Ubuntu 24.04, Docker Compose). Client,
  server, sign-in service and database run in separate containers behind one public origin.
- Build: Maven (JDK 25) builds the jars, Docker builds an image per service; the SPA is built by Vite
  (`VITE_API_BASE=/api`; it signs in at its own origin, so the image fits every domain) and served by
  nginx with an SPA fallback.
- HTTPS: Caddy as the only public entry point with automatic Let's Encrypt certificates, HSTS and
  security headers; the internal accounts API and the actuators are not exposed.
- Environment variables: `infra/deploy/.env` (gitignored, generated secrets), `.env.example` in the
  repository; each container gets only its own secrets.
- CORS: the gateway allows only the deployed client origin; the SPA, the API and the sign-in share it.
- Database: PostgreSQL 18 in a container with a persistent volume, one database and user per service,
  passwords from the environment, daily `pg_dumpall` backups.
- CI/CD: GitHub Actions runs the tests on every push; pushes to `main` build multi-architecture images
  into GHCR and roll them out over SSH.
- Difficulties met while preparing it: an identity provider behind a proxy must see the public
  scheme, host and port (`X-Forwarded-*`), otherwise tokens carry the wrong issuer and the services
  answer 401, or redirects go to the container port; a bind-mounted secret file must be readable by
  the container user; one Telegram token can be polled by one instance only.
