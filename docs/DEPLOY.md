# Deployment — «Розклад ВТФК» on one VPS

The whole system runs on one Linux server behind Caddy, which gets Let's Encrypt certificates by
itself. You create the VM, point a domain at it, fill one env file and run one command:

```bash
infra/deploy/scripts/deploy.sh
```

The same command updates the server later. GitHub Actions can run it for you on every push to
`main` (section 13).

## 1. Layout

```
Internet ──► :80 / :443  Caddy (TLS, HTTP/2 + HTTP/3, security headers, compression)
              ├─ https://DOMAIN/            → web:80        nginx + Vite build, SPA fallback
              ├─ https://DOMAIN/api/*       → gateway:8080  → core, scheduler, importer, notification
              ├─ https://auth.DOMAIN/       → keycloak:8080 only /realms, /resources, /.well-known
              └─ https://api.DOMAIN/api/*   → gateway:8080  optional, for the Netlify client (section 14)

Internal network only (no published ports): postgres, rabbitmq, redis, keycloak, the services.
```

| File | What it does |
|---|---|
| `infra/deploy/compose.prod.yml` | Overlay on `infra/docker-compose.yml`: Caddy, no published ports for anything else, Keycloak in production mode, secrets from env, memory limits, log rotation |
| `infra/deploy/caddy/Caddyfile` | Sites, TLS, routing, `/admin` of Keycloak closed, CSP fix for the SPA, forged forwarding headers removed |
| `infra/deploy/.env.example` → `infra/deploy/.env` | Every setting with comments. `.env` is gitignored |
| `infra/deploy/keycloak/rozklad-realm.prod.json` | Production realm: no dev users, no localhost URLs, secrets via `${ENV}` placeholders |
| `infra/deploy/keycloak/demo-users.json` | Demo accounts for the defense (no passwords inside) |
| `infra/deploy/postgres/20-prod-passwords.sh` | Replaces the dev passwords of `init.sql` on the first start |
| `infra/deploy/scripts/` | `deploy.sh`, `gen-secrets.sh`, `compose.sh`, `keycloak-sync.sh`, `create-demo-users.sh`, `backup-db.sh`, `restore-db.sh`, `ci-entry.sh` (what the GitHub key may run) |
| `infra/deploy/.env.images` | Written by `deploy.sh`: which images run now (gitignored, do not edit) |
| `web/netlify.toml`, `infra/deploy/netlify/postbuild.mjs` | Variant B: the client on Netlify |
| `.github/workflows/ci.yml`, `deploy.yml` | CI and auto-deploy |

How this covers the coursework requirements (level A):

| Requirement | Here |
|---|---|
| Permanent public HTTPS link | `https://DOMAIN`, certificates renewed by Caddy, the VM is always on (no cold starts) |
| Client, server and database deployed separately | Separate containers and origins: nginx with the SPA, Spring services behind the gateway, PostgreSQL; variant B moves the client to Netlify |
| Secrets only in environment variables | `infra/deploy/.env` (gitignored), generated by `gen-secrets.sh`; the repo has only `.env.example` |
| CORS for the deployed client | Gateway `CORS_ALLOWED_ORIGINS` = `https://DOMAIN` (+ the Netlify origin) |
| SPA routing on the static server | nginx `try_files … /index.html`; Netlify `/* /index.html 200` |
| Test credentials | Demo accounts from `.env` (section 9) |
| Auto-deploy from `main` with GitHub Actions | `.github/workflows/deploy.yml` |

## 2. Create the server

Recommended: 4 vCPU, 8+ GB RAM, 40+ GB disk, Ubuntu 24.04, x86_64 or ARM64; for the defense take
8 GB or the Oracle A1 VM below. The memory limits of the containers add up to about 6 GB (they are
caps, not reservations). 2 vCPU / 4 GB with 2 GB of swap is best effort and has not been measured:
on such a server let GitHub Actions build the images (section 13) instead of building on the VPS,
and watch `docker stats --no-stream` while the solver runs.

**Oracle Cloud Always Free (recommended, 4 OCPU / 24 GB ARM64, free).**

1. Sign up at cloud.oracle.com. A card is checked but Always Free resources are not charged. The
   **home region cannot be changed later** and the free A1 capacity exists only there: pick one close
   to Ukraine (Frankfurt, Amsterdam, Stockholm…).
2. Compute → Instances → Create instance.
   - Image: Canonical Ubuntu 24.04. Shape: Ampere → `VM.Standard.A1.Flex`, 4 OCPU, 24 GB.
   - Networking: create a VCN with a public subnet, "Assign a public IPv4 address".
   - SSH keys: upload your public key (`~/.ssh/id_ed25519.pub`) or download the generated one.
   - Boot volume: 100 GB is plenty (200 GB of block storage are free in total).
3. "Out of capacity" is common for A1: try another availability domain, try again later, or take
   2 OCPU / 12 GB for now.
4. To keep the address when the VM is recreated, make the public IP **reserved** (Networking → IP
   management → Reserved public IPs, then attach it on the instance's VNIC).
5. Oracle may reclaim Always Free VMs that stay idle for 7 days (CPU, network and, for A1, memory
   under 20 %). Upgrading the account to Pay As You Go keeps the free resources free and stops that.

Log in: `ssh ubuntu@<public-ip>`.

**Other options.** Azure for Students ($100 credit, no card): a `B2s` / `B2als v2` VM with 4 GB and
Ubuntu 24.04 lasts a few months on the credit (a 4 GB size is best effort, see above; `B2ms` has
8 GB). Any other VPS works the same way; the user name may be `root` or `azureuser` instead of
`ubuntu`.

## 3. Open ports 80 and 443, prepare the OS

Ports 80 and 443 must be open in **two places**: the cloud firewall and the OS firewall. Port 80 is
needed for the Let's Encrypt challenge and the redirect to HTTPS. UDP 443 (HTTP/3) is optional.

Cloud firewall:
- Oracle: Networking → Virtual cloud networks → your VCN → Security Lists → Default Security List →
  Add Ingress Rules: source `0.0.0.0/0`, TCP, destination port `80`; the same for `443`
  (optionally UDP `443`).
- Azure: VM → Networking → Add inbound port rule: 80 and 443 (TCP).

OS firewall. Oracle's Ubuntu images ship iptables rules that reject everything except SSH. Open the
ports **before installing Docker**, so the saved rules do not contain Docker's own chains:

```bash
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p udp --dport 443 -j ACCEPT
sudo netfilter-persistent save
sudo iptables -L INPUT -n --line-numbers   # the three ACCEPT lines must be above the REJECT line
```

On images with ufw instead (Azure, most VPS): `sudo ufw allow OpenSSH && sudo ufw allow 80,443/tcp &&
sudo ufw allow 443/udp && sudo ufw enable`. Docker publishes ports with its own iptables rules that
bypass ufw; that is one more reason why only Caddy publishes ports here.

Docker Engine with the Compose plugin (the official script works on x86_64 and ARM64):

```bash
curl -fsSL https://get.docker.com -o get-docker.sh && sudo sh get-docker.sh
sudo usermod -aG docker "$USER"     # log out and back in for this to apply
docker compose version              # needs 2.24.4 or newer
```

On a 4 GB server add 2 GB of swap (builds and the first start of Keycloak need it):

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Optional: `sudo timedatectl set-timezone Europe/Kyiv` (cron times of the backup), and keep
`unattended-upgrades` on (it is preinstalled on Ubuntu cloud images).

## 4. Domain names

Three host names point to the server: `DOMAIN`, `auth.DOMAIN` and, for variant B only, `api.DOMAIN`.

| Option | DOMAIN | DNS work |
|---|---|---|
| sslip.io (free, nothing to register) | `203-0-113-10.sslip.io` for IP 203.0.113.10 | none: `auth.203-0-113-10.sslip.io` resolves to the same IP |
| DuckDNS (free) | `rozklad-vtfk.duckdns.org` | create the name at duckdns.org with the server IP; sub-names resolve to it too |
| GitHub Student Developer Pack | a free domain for a year from a partner registrar (see education.github.com/pack for the current offer) | A records below |
| Own domain | `rozklad.example.org` | A records below |

A records for your own domain (or one wildcard `*.rozklad` plus `rozklad`):

| Type | Name | Value |
|---|---|---|
| A | `rozklad` | server IP |
| A | `auth.rozklad` | server IP |
| A | `api.rozklad` | server IP (variant B only) |

Check before deploying: `getent hosts rozklad.example.org auth.rozklad.example.org` on the server
(or `nslookup` on Windows). sslip.io depends on the IP never changing (reserve it) and on a public
DNS service; Let's Encrypt raised its limits for sslip.io/nip.io, and if a certificate is still
refused, `<ip>.nip.io` or a DuckDNS name works the same way.

## 5. Get the code and configure

```bash
git clone https://github.com/<user>/<repo>.git ~/rozklad
cd ~/rozklad
infra/deploy/scripts/gen-secrets.sh     # creates infra/deploy/.env, fills every "change-me"
nano infra/deploy/.env
```

A private repository needs a read-only deploy key on the server: `ssh-keygen -t ed25519 -f
~/.ssh/rozklad_deploy -N ''`, add `~/.ssh/rozklad_deploy.pub` in GitHub → repository → Settings →
Deploy keys, then clone with `GIT_SSH_COMMAND='ssh -i ~/.ssh/rozklad_deploy' git clone
git@github.com:<user>/<repo>.git ~/rozklad` and run `git config core.sshCommand 'ssh -i
~/.ssh/rozklad_deploy'` inside the clone.

Set by hand in `infra/deploy/.env`:

| Key | Value |
|---|---|
| `DOMAIN` | host name only, e.g. `rozklad.example.org` or `203-0-113-10.sslip.io` |
| `ACME_EMAIL` | your real e-mail (Let's Encrypt refuses example.com) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_CHAT_ID`, `TELEGRAM_BOT_USERNAME` | from @BotFather / your chat (section 10) |
| `ANTHROPIC_API_KEY` | from console.anthropic.com; empty disables AI import |
| memory block at the end | uncomment it on Oracle A1 (24 GB); keep the defaults on 4–8 GB |

Everything else has a working default or was generated. The secrets never leave this file: compose
passes each service only what it needs. Keep a copy of `.env` in a password manager — backups and
the Keycloak clients depend on these values.

Create the backup directory once: `sudo install -d -m 700 -o "$USER" /var/backups/rozklad`.

## 6. First start

```bash
infra/deploy/scripts/deploy.sh
```

What it does:

1. `git pull --ff-only` and continues with the scripts it just pulled (`--no-pull` skips this).
2. Preflight: Docker and Compose versions, no `change-me` left, sane `DOMAIN`/`ACME_EMAIL`, the
   compose configuration renders, warning about RAM without swap.
3. Builds the jars with Maven in a `maven:3.9.11-eclipse-temurin-25` container (no JDK on the host,
   dependencies cached in `~/.m2`), then the images `localhost/rozklad/<service>:prod` for this CPU
   (`compose build --pull`). With GitHub-built images it pulls them instead (section 13). Either way
   it records the images in `infra/deploy/.env.images`, so `compose.sh` and `restore-db.sh` keep
   using exactly those.
4. `compose up -d --wait`: PostgreSQL creates the databases (dev `init.sql`, then the production
   passwords), Keycloak builds itself and imports the realm, the services start, Caddy requests the
   certificates.
5. `caddy reload` (a changed Caddyfile takes effect), `keycloak-sync.sh` writes the web origins and
   client secrets from `.env` into Keycloak, `create-demo-users.sh` creates, updates or disables the
   demo accounts.
6. Smoke checks through Caddy (SPA, API, per-client rate limit with forged `Forwarded` headers,
   issuer, OIDC authority baked into the SPA, `/admin` closed, CSP, certificates) and a summary.
   In pull mode it then removes the images of older deploys, keeping the current and the previous
   one.

The first run downloads a lot (Maven dependencies, LibreOffice packages for two images, npm
packages) and takes roughly 15–30 minutes; Keycloak alone needs about 2 minutes on its first start.
Later runs take a few minutes. If a step fails, the script stops with the command to look at; it is
safe to run again.

## 7. Check that it works

```bash
D=rozklad.example.org    # your DOMAIN
curl -sI https://$D/ | grep -iE '^(HTTP|strict-transport|content-security-policy)'
curl -s https://auth.$D/realms/rozklad/.well-known/openid-configuration | grep -o '"issuer":"[^"]*"'
curl -s -o /dev/null -w '%{http_code}\n' https://auth.$D/admin/             # 404: admin console closed
curl -si https://$D/api/public/does-not-exist | grep -iE '^(HTTP|x-request-id)'   # the gateway answered
curl -sI http://$D/ | grep -i '^location'                                    # redirect to https
```

Expected: `HTTP/2 200` with HSTS and a CSP that contains `https://auth.DOMAIN`; issuer
`https://auth.DOMAIN/realms/rozklad`; `404`; a 404 with an `X-Request-Id` header; `location:
https://…`.

In the browser: open `https://DOMAIN`, log in as `admin`, open the admin pages; in a private window
log in as `krentsin`. Live updates (SSE) can be checked with a token copied from the browser
(DevTools → Network → any `/api` request → `Authorization` header):

```bash
curl -N -H "Authorization: Bearer <token>" https://$D/api/events/stream    # "event: ping" every ~25 s
```

For the explanatory note, run Lighthouse (mobile) against `https://DOMAIN` here.

## 8. Before the defense

- Open the site from a phone on mobile data (not the server's network) and log in with both roles.
- Check that the bot answers and no other instance polls the same token (section 10).
- Make a backup (`infra/deploy/scripts/backup-db.sh`) and copy it to your PC.
- Do not deploy in the last hours before the defense.

## 9. Accounts for the examiner

`deploy.sh` creates them in the realm `rozklad` with the passwords from `.env`:

| Login | Role | Password |
|---|---|---|
| `admin` | ADMIN (dispatcher) | `DEMO_ADMIN_PASSWORD` |
| `krentsin` | TEACHER | `DEMO_TEACHER_PASSWORD` |
| `nepyivoda` | TEACHER | `DEMO_TEACHER_PASSWORD` |

Give them in the explanatory note or on paper, never in the repository. They keep the ids of the
development realm, so demo data that links the teachers «Кренцін» and «Непийвода» to those ids works
on the server too. To change a password, edit `.env` and run `infra/deploy/scripts/create-demo-users.sh`.
After the defense empty both `DEMO_*_PASSWORD` values and run the same script: an empty password
disables the account, and every later `deploy.sh` (also the GitHub one) and `restore-db.sh` keeps it
disabled. Check with the `kcadm` commands of section 11 (`enabled` is `false`). Real teachers join through
invites (`/invite/{token}`); self-registration is off. Passwords need at least 8 characters and must
differ from the login and the e-mail; five wrong attempts lock an account for a minute or more.

## 10. Telegram bot

Long polling (the default `TELEGRAM_MODE=POLLING`) needs no inbound connection, but **one bot token
can be polled by one process only**. A second poller makes Telegram answer `409 Conflict: terminated
by other getUpdates request` and the two instances steal updates from each other. Before starting
the server, stop the notification service on your PC (or the local `--profile app` stack), or better:
create a second bot in @BotFather for development and keep its token in your local `.env`.

`TELEGRAM_OWNER_CHAT_ID` is your chat id (write to the bot, then read `chat.id` from
`https://api.telegram.org/bot<token>/getUpdates` while no instance is polling). Webhook mode, if the
notification service is configured for it, uses `https://DOMAIN/api/notify/telegram/webhook` and the
`TELEGRAM_WEBHOOK_SECRET` header check; Caddy already provides the HTTPS endpoint.

## 11. Day-to-day operations

`infra/deploy/scripts/compose.sh` is `docker compose` with the production files; use it for
everything:

```bash
cd ~/rozklad
infra/deploy/scripts/deploy.sh                               # update to the latest main (see below)
infra/deploy/scripts/compose.sh ps                           # status and health
infra/deploy/scripts/compose.sh logs -f --tail=100 core      # follow one service
infra/deploy/scripts/compose.sh logs --since=1h notification | grep -i error
infra/deploy/scripts/compose.sh restart notification         # same container, same environment
infra/deploy/scripts/compose.sh up -d                        # apply .env changes (recreates what changed)
infra/deploy/scripts/compose.sh exec postgres psql -U postgres -d core
infra/deploy/scripts/compose.sh exec rabbitmq rabbitmqctl list_queues name messages consumers
docker stats --no-stream                                     # memory per container
```

The Java services log JSON (ECS). Readable view: `sudo apt-get install -y jq`, then
`infra/deploy/scripts/compose.sh logs --no-log-prefix core | jq -r '"\(.["@timestamp"]) \(.["log.level"]) \(.message)"'`.
Docker rotates the logs: 5 files × 10 MB per container.

`compose.sh` always uses the images recorded in `infra/deploy/.env.images` by the last `deploy.sh`
(also the one GitHub ran), so `compose.sh up -d` never switches images behind your back. `restart`
keeps a container's old environment: after changing `.env` use `up -d`.

Which images `deploy.sh` rolls out: `IMAGE_PREFIX`/`IMAGE_TAG` from the environment, else from `.env`,
else the recorded ones, else `localhost/rozklad/<service>:prod` built on the server. So on a server fed
by GitHub Actions a manual `deploy.sh` pulls the scripts and compose files of `main` and starts the
same images again; new images come only from the Deploy workflow. `deploy.sh --build` builds on the
server instead.

`DOMAIN` and `TELEGRAM_BOT_USERNAME` are baked into the SPA when the web image is built:

- images built on the server: change `.env`, then run `deploy.sh` (not only `compose.sh up -d`);
- images from GitHub Actions: change `.env` on the server **and** the repository variables `DOMAIN` /
  `TELEGRAM_BOT_USERNAME`, then run the Deploy workflow (Actions → Deploy → Run workflow on `main`).
  A manual `deploy.sh` only pulls the existing web image, which still points to the old Keycloak.
  `ci-entry.sh` refuses to deploy while the two `DOMAIN` values differ, and the smoke checks warn when
  the SPA was built for another Keycloak than the one in `.env`.

A new `DOMAIN` also gets new certificates and new Keycloak redirect URIs automatically.

Rollback to an earlier commit:

```bash
git log --oneline -10
git checkout <good-commit> && infra/deploy/scripts/deploy.sh --no-pull
git checkout main                              # later, to follow main again
```

With images from GitHub Actions: `IMAGE_TAG=<good-commit-sha> infra/deploy/scripts/deploy.sh --no-pull
--pull-images` (the prefix comes from the record). The previous deploy's images stay on the server;
older ones are pulled again, which needs `docker login ghcr.io` for private packages (section 13).
Database migrations only go forward (Flyway), so roll back only to a commit with the same schema, or
restore a backup.

Keycloak admin console: set `KC_ADMIN_ALLOWED=1`, run `infra/deploy/scripts/compose.sh up -d caddy`,
open `https://auth.DOMAIN/admin/` and log in with `KEYCLOAK_ADMIN_USER` / `KEYCLOAK_ADMIN_PASSWORD`;
afterwards set it back to `0` and run the same command. Without opening anything, the CLI works too:

```bash
infra/deploy/scripts/compose.sh exec keycloak bash
kc=/opt/keycloak/bin/kcadm.sh
$kc config credentials --server http://localhost:8080 --realm master \
  --user "$KC_BOOTSTRAP_ADMIN_USERNAME" --password "$KC_BOOTSTRAP_ADMIN_PASSWORD" --config /tmp/kc.cfg
$kc get users -r rozklad --fields username,enabled --config /tmp/kc.cfg
rm /tmp/kc.cfg; exit
```

`KEYCLOAK_ADMIN_PASSWORD` is applied only on the very first start. Change it in the console first,
then in `.env`, otherwise the scripts cannot log in.

## 12. Backups and restore

```bash
infra/deploy/scripts/backup-db.sh        # all databases incl. Keycloak → /var/backups/rozklad/rozklad-<date>.sql.gz
crontab -e                               # daily at 03:15, keeps BACKUP_KEEP_DAYS (14) days:
15 3 * * * $HOME/rozklad/infra/deploy/scripts/backup-db.sh >>$HOME/rozklad-backup.log 2>&1
```

A dump is the whole cluster: every account, Telegram chat bindings, Keycloak's client secrets and
password hashes. On the server the files are readable by your user only. Copy them off now and then,
but **encrypted**, and never next to `.env` (that file belongs in a password manager, section 5).
With [age](https://age-encryption.org) (Windows: `winget install FiloSottile.age`), on your PC:

```bash
age-keygen -o rozklad-backup.key        # once; keep this file in the password manager, not with the dumps
# the public key is the "public key: age1..." line it printed
ssh ubuntu@<ip> 'cat /var/backups/rozklad/rozklad-20261107-031500.sql.gz' |
  age -r age1... -o rozklad-20261107-031500.sql.gz.age      # the plain dump never lands on the PC
age -d -i rozklad-backup.key -o rozklad-20261107-031500.sql.gz rozklad-20261107-031500.sql.gz.age   # to restore
```

A password-protected 7-Zip archive with encrypted file names (`7z a -p -mhe=on`) works too; delete the
plain `.sql.gz` copies afterwards.

Restore (destructive: every database is replaced):

```bash
infra/deploy/scripts/restore-db.sh /var/backups/rozklad/rozklad-20261107-031500.sql.gz --yes
```

It first checks that the recorded images are on the server (otherwise it stops before touching
anything), then stops everything except PostgreSQL, loads the dump (two errors about the role
`postgres` are expected), sets the service passwords from the current `.env` again, starts the same
images and syncs the Keycloak clients and demo accounts with `.env`. On a new server: deploy first,
then restore.

Volumes: `pgdata` holds all data. `rabbitdata` (queued messages), `redisdata` (caches, bot dialogs)
and `caddy_data` (certificates, re-issued automatically) can be lost without harm.
`infra/deploy/scripts/compose.sh down -v` deletes all of them.

## 13. GitHub Actions

- **CI** (`.github/workflows/ci.yml`) runs on pull requests and on pushes to other branches: Maven
  `verify` on JDK 25 (unit tests and Testcontainers integration tests with the runner's Docker),
  web `npm ci`, lint, tests, build, and checks of this deployment setup (compose overlay, Caddyfile,
  shell scripts, realm JSON).
- **Deploy** (`.github/workflows/deploy.yml`) runs on every push to `main` and by hand: it calls CI,
  and only if CI passes builds the images for `linux/amd64` and `linux/arm64`, pushes them to
  `ghcr.io/<owner>/rozklad/<service>:<commit-sha>` and `:latest`, then connects to the server over
  SSH and runs `infra/deploy/scripts/ci-entry.sh`, which runs `deploy.sh --pull-images` with that
  tag. A manual run on any branch other than `main` runs CI only.

Deploy does nothing but CI until it is configured (GitHub → repository → Settings → Secrets and
variables → Actions):

| Kind | Name | Value |
|---|---|---|
| secret | `VPS_HOST` | server IP or DOMAIN |
| secret | `VPS_USER` | `ubuntu` (the user that owns `~/rozklad` and is in the `docker` group) |
| secret | `VPS_SSH_KEY` | private key of a key pair made for GitHub (below) |
| secret | `VPS_KNOWN_HOSTS` | the server's host key (below); the deploy job fails without it |
| secret, optional | `VPS_PORT` | SSH port if not 22 |
| variable | `DOMAIN` | the same value as in `.env` (it is baked into the web image) |
| variable, optional | `IMAGE_PLATFORMS` | `linux/arm64` for Oracle A1 only: about half the build time |
| variable, optional | `VPS_APP_DIR` | clone directory on the server, default `rozklad` (= `~/rozklad`) |
| variable, optional | `TELEGRAM_BOT_USERNAME` | bot link on the About page |

Deploy key for GitHub. The `docker` group is root-equivalent, so the key must not open a shell: it
gets a forced command and may run `ci-entry.sh` only. On your PC:

```bash
ssh-keygen -t ed25519 -C github-deploy -f rozklad_github -N ''
cat rozklad_github.pub                         # one line: ssh-ed25519 AAAA... github-deploy
```

On the server, append that line to `~/.ssh/authorized_keys` **with this prefix** (adjust the path if
the clone is not `~/rozklad` of the user `ubuntu`):

```
restrict,command="bash /home/ubuntu/rozklad/infra/deploy/scripts/ci-entry.sh" ssh-ed25519 AAAA... github-deploy
```

`restrict` turns off port forwarding, agent forwarding and the terminal; `command` makes sshd run
`ci-entry.sh` whatever the client asks. The script reads the commit sha, image prefix, user name,
token and `DOMAIN` from stdin, accepts only a 40-character sha and `ghcr.io/<owner>/rozklad`, and runs
`deploy.sh --pull-images`. Paste the private key (`rozklad_github`) into the `VPS_SSH_KEY` secret,
then delete both files.

Host key: on the server run `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`; on your PC run
`ssh-keyscan -t ed25519 <VPS_HOST>` (the same name or IP as the secret; `-p <port>` if not 22), check with `ssh-keygen -lf -` on that
output that the fingerprint is the same, and paste the `ssh-keyscan` line into `VPS_KNOWN_HOSTS`. The
runner never trusts a key it has not been given.

Also, in GitHub → Settings → Environments → `production` → Deployment branches and tags, allow only
`main`. The workflow already skips other branches; the rule makes GitHub enforce it too.

Leave `IMAGE_PREFIX`/`IMAGE_TAG` unset in the server's `.env`. `deploy.sh` records what the workflow
deployed in `infra/deploy/.env.images`, and manual runs start those images again. The workflow logs
the server in to GHCR with the job's own token for the duration of the job, so the packages may stay
private; pulling other tags by hand needs `docker login ghcr.io` with a token that has
`read:packages`, or public packages. The server still runs `git pull` for the compose files and
scripts (deploy key for a private repo, section 5).

The first image build takes long (ARM64 is emulated with QEMU, LibreOffice and npm run inside it);
later builds reuse the GitHub Actions cache.

## 14. Variant B: client on Netlify, API on the VPS

The SPA can also be hosted on Netlify while the API, Keycloak and the database stay on the VPS.

1. VPS `.env`: `API_SITE_ENABLED=1` and `EXTRA_WEB_ORIGIN=https://<site>.netlify.app` (exact origin,
   no trailing slash); DNS record for `api.DOMAIN` (sslip.io and DuckDNS need nothing); run
   `deploy.sh`. Caddy serves `https://api.DOMAIN/api/*`, the gateway allows the Netlify origin
   (CORS), and Keycloak gets its redirect URIs.
2. Netlify: import the repository from GitHub and set **Base directory `web`** (the build command and
   the publish directory come from `web/netlify.toml`). Environment variables:

   | Variable | Value |
   |---|---|
   | `VITE_API_BASE` | `https://api.DOMAIN/api` |
   | `VITE_OIDC_AUTHORITY` | `https://auth.DOMAIN/realms/rozklad` |
   | `VITE_OIDC_CLIENT_ID` | `rozklad-web` |
   | `VITE_TELEGRAM_BOT_URL` | `https://t.me/<bot>` |

3. Deploy. `netlify.toml` adds the SPA fallback (`/* /index.html 200`), security headers and
   long caching of `/assets/*`; `infra/deploy/netlify/postbuild.mjs` writes `dist/_headers` with the
   Content-Security-Policy of `web/nginx.conf`, adapted to the API and Keycloak origins of the
   variables above, and drops the source maps.

The site on the VPS keeps working in parallel. Netlify builds on every push by itself.

## 15. Troubleshooting

**`exec format error`, a container restarts at once.** The image was built for another CPU. Build on
the server (`deploy.sh --build`) or include its platform in `IMAGE_PLATFORMS`. Check with
`docker image inspect localhost/rozklad/core:prod --format '{{.Architecture}}'` (or the ghcr.io name) and `uname -m`
(`aarch64` = `arm64`).

**No certificate / the browser warns.** DNS of `DOMAIN` and `auth.DOMAIN` must point to the server,
TCP 80 and 443 must be open in both firewalls. `infra/deploy/scripts/compose.sh logs caddy | grep -iE
'error|challenge'`. After too many failures Let's Encrypt pauses for an hour: switch `ACME_CA` to the
staging URL while experimenting, then back, and run `compose.sh up -d caddy` each time (`restart`
keeps the old environment, so Caddy would stay on the old CA). With `ACME_CA` on staging browsers
always warn.

**Ports are open in the cloud but connections time out (Oracle).** `sudo iptables -L INPUT -n
--line-numbers` (section 3); `sudo iptables -L FORWARD -n | head`: Docker's chains must come before
`REJECT` — `sudo systemctl restart docker` puts them back on top.

**Keycloak does not start.** `compose.sh logs keycloak`. Usual causes: wrong `KC_DB_PASSWORD` after
the database was initialised with other values (section on PostgreSQL below); too little memory on
the first start (swap); `KC_HOSTNAME` must be a full `https://auth.DOMAIN` URL — compose builds it from
`DOMAIN`. The first start needs about 2 minutes.

**"Invalid parameter: redirect_uri" on login.** Keycloak does not know the origin of the page. Run
`infra/deploy/scripts/keycloak-sync.sh` (deploy.sh does it), and for Netlify check that
`EXTRA_WEB_ORIGIN` equals the site origin exactly.

**"HTTPS required".** A request reached Keycloak without Caddy's `X-Forwarded-Proto: https`.
Keycloak is only reachable through Caddy here; check that you use `https://auth.DOMAIN`, not the IP.

**Every API call returns 401 after a successful login (issuer mismatch).** Services accept only tokens
whose `iss` equals `KEYCLOAK_ISSUER` = `https://auth.DOMAIN/realms/rozklad`. Compare with the discovery
document (section 7) and with the token (paste it into jwt.io or decode the middle part). Tokens from
the development Keycloak (`http://localhost:8180`) or from a Keycloak opened through the IP are
rejected; so are tokens issued before `DOMAIN` changed: log in again.
`compose.sh exec core printenv KEYCLOAK_ISSUER` shows what the service expects.

**Login page does not open, browser console says "Refused to connect … Content-Security-Policy".**
The SPA's CSP must allow `https://auth.DOMAIN`. Caddy rewrites `http://localhost:8180` in the CSP of
`web/nginx.conf`; if nginx.conf no longer contains that value, update `header_down` in
`infra/deploy/caddy/Caddyfile` and run `deploy.sh`, which reloads Caddy (by hand: `compose.sh exec
caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile`). `deploy.sh` warns about this.

**Live updates (SSE) arrive late, in bursts, or stop.** The Caddyfile flushes `/api/events/stream`
immediately and does not compress it; the gateway route has no response timeout; core sends `ping`
every 25 s, so idle proxies do not cut the stream, and the SPA reconnects. Test with `curl -N`
(section 7). An extra proxy in front (Cloudflare and the like) has to be configured not to buffer.

**CORS errors (variant B).** `EXTRA_WEB_ORIGIN` must be exactly `https://<site>.netlify.app`. Check the
preflight: `curl -si -X OPTIONS https://api.DOMAIN/api/public/x -H 'Origin: https://<site>.netlify.app'
-H 'Access-Control-Request-Method: GET' | grep -i access-control-allow-origin`. The main layout is
same-origin and needs no CORS.

**429 Too Many Requests on public pages.** The gateway limits `/api/public/**` per client IP
(`PUBLIC_RATE_LIMIT_PER_SECOND`, `PUBLIC_RATE_LIMIT_BURST`). Behind Caddy the gateway reads the real
client IP from `X-Forwarded-For` (`SERVER_FORWARD_HEADERS_STRATEGY=native`), so one user cannot
exhaust the limit of everyone. Caddy writes that header itself and removes the client's `Forwarded`,
`X-Forwarded-Port` and `X-Forwarded-Prefix` (snippet `strip_client_forwarding`); otherwise a forged
`Forwarded: for=...` would give every request a fresh bucket. Raise the values in `.env` if needed
and run `compose.sh up -d`.

**PostgreSQL: "password authentication failed for user core".** The init scripts run only when the
volume is created. If the first start failed half-way, on a fresh server remove the volumes and start
again: `infra/deploy/scripts/compose.sh down -v && infra/deploy/scripts/deploy.sh` (**deletes all
data**). On a server with data, set the passwords from `.env` instead:
`infra/deploy/scripts/compose.sh exec postgres bash /docker-entrypoint-initdb.d/20-prod-passwords.sh`.

**Containers restart, `docker stats` shows them at the limit, `dmesg | grep -i oom` has entries.**
Add swap or raise the limits (memory block in `.env`); the JVMs exit on `OutOfMemoryError` and Docker
restarts them.

**Telegram: `409 Conflict`.** Another instance polls the same token (section 10).

**Disk full.** `docker system df`; `docker builder prune -f` and `docker image prune -f` free most of
it. `deploy.sh` prunes dangling images itself and, with GitHub-built images, removes the commit tags
of older deploys (it keeps the current and the previous one). Pulled tags of another prefix are not
touched: `docker image ls` and `docker image rm` them by hand.

## 16. For the explanatory note (section 4.7.9)

- Platform: one VPS (Oracle Cloud Always Free, Ampere A1, Ubuntu 24.04, Docker Compose). Client,
  server and database run in separate containers and are reachable on separate origins; variant B
  moves the client to Netlify.
- Build: Maven (JDK 25) builds the jars, Docker builds an image per service; the SPA is built by Vite
  with the production URLs (`VITE_OIDC_AUTHORITY`, `VITE_API_BASE`) and served by nginx with an SPA
  fallback.
- HTTPS: Caddy as the only public entry point with automatic Let's Encrypt certificates, HSTS and
  security headers; Keycloak's admin console and the master realm are not exposed.
- Environment variables: `infra/deploy/.env` (gitignored, generated secrets), `.env.example` in the
  repository; each container gets only its own secrets.
- CORS: the gateway allows only the deployed client origin(s).
- Database: PostgreSQL 18 in a container with a persistent volume, one database and user per service,
  passwords from the environment, daily `pg_dumpall` backups.
- CI/CD: GitHub Actions runs the tests on every push; pushes to `main` build multi-architecture images
  into GHCR and roll them out over SSH.
- Difficulties met while preparing it: Keycloak in production mode needs the public hostname and proxy
  headers, otherwise tokens carry the wrong issuer and the services answer 401; the SPA's CSP named
  the development Keycloak; the JVM option `-XX:MaxHeapFreeRatio=30` from the Keycloak docs stopped
  the JVM from starting; the base health check of Keycloak reported "ready" too early; one Telegram
  token can be polled by one instance only.

## 17. What has been verified

Verified while preparing this setup (on the development PC, without building the application images):
the overlay renders with `.env.example` and publishes only Caddy's ports; the Caddyfile validates in
every toggle combination and, run against stub upstreams, routes, closes `/admin` and `/realms/master`,
rewrites the CSP, sets the headers, leaves SSE uncompressed and redirects HTTP to HTTPS; PostgreSQL,
Redis and Keycloak started from this overlay in an isolated compose project: the production realm was
imported with the placeholders resolved, a client-credentials token fetched over the internal URL
carried the public issuer, the dev secret and dev users are gone, `keycloak-sync.sh`,
`create-demo-users.sh` (fixed ids, password login), `backup-db.sh` and the database part of
`restore-db.sh` worked, the service passwords from `.env` are required and the dev ones are refused;
`gen-secrets.sh` was tested on throwaway files; the scripts pass `bash -n` and ShellCheck, the
workflows pass actionlint, the Netlify post-build produces the same script hash as `web/nginx.conf`.
After the review: Caddy (2.11) was checked to drop client `Forwarded`, `X-Forwarded-Port`,
`X-Forwarded-Prefix` and `X-Real-IP` and to replace `X-Forwarded-For` before proxying; the overlay
renders with `.env.images` taking precedence over `.env`; `docker compose config --images` lists the
images `restore-db.sh` checks; the default `localhost/rozklad` prefix cannot be resolved on Docker Hub.
